# MUKE 后台与 Lark Base 权限接入决策

核对日期：2026-10-18（上海）。这是工程接入依据，不是已部署的员工授权名单。没有修改 Base 角色、应用权限或 AnyCross 发布版本。

## 已核实的限制

MUKE-Lite 当前只有应用身份的 `bitable:app:readonly` 和 `im:message:send_as_bot`。用户身份的记录查询权限尚未开通。控制台存在更小的 `base:record:retrieve` 用户权限，但本次没有勾选或申请。

Lark 的[查询记录文档](https://open.larksuite.com/document/uAjLw4CM/ukTMukTMukTM/reference/bitable-v1/app-table-record/search)（页面标注更新于 2026-03-12）同时说明了两个边界：

- 用户令牌代表登录用户，数据访问范围取决于该用户。
- 对开启高级权限的 Base，调用身份需要可管理权限，否则可能得到成功但为空的结果。

因此，不能把“使用 user_access_token”当成“可以完整继承当前员工的行、列、视图权限”的实现保证。普通员工的真实账号对照测试仍缺失。不得为了让 API 返回数据而提升员工到 Base 管理员，不得把空结果自动解释成没有招聘或没有员工，更不得自动切换到应用管理员令牌。

## 当前角色配置样本

以下是角色配置，不是某个人的最终有效权限。人员可能属于多个角色、部门或管理组，合并规则与实际成员归属还需核验。

| 角色和表 | 页面核实结果 | 新后台设计约束 |
| --- | --- | --- |
| HR / A01 招聘需求 | 所有记录、字段、视图可阅读 | 不因 HR 身份就开放发布、停招、删除；这些是额外业务授权 |
| HR / H01 员工 | 所有记录可编辑，但只有指定字段可编辑；不可新增、删除记录 | 分离查看、局部编辑、入职建档；不可提供任意字段更新接口 |
| HR / H07 异动、H09 离职 | 无权限 | 暂不接入 HR 的异动、离职操作 |
| T2-Agent / A05 简历 | Agent 人员字段包含本人；部分字段可阅读；仅指定视图可见 | 必须核实当前登录人与 Agent 的身份映射，服务端限定记录与响应字段 |
| T2-Agent / H01 员工 | 全部记录、字段可阅读，但仅建档视图可见 | 不把视图可见性当成行级隔离；不直接搬运为全员档案接口 |

本次 H01 / HR 页面显示可编辑的字段：Team、Start、Lark Name、Add Lark、Stage、CONT、Sign Video、Level、Kit、ASST、Notes、Exit Date、TRI Start、APMT、🚫NHR Reason。它们只是现有角色上限，不能据此立刻开放写入；部分字段可能触发公式、自动化、合同或通知，须逐项建立依赖。

本次 A05 / T2-Agent 页面显示 Emp Status、JOB、Sort Key 不可阅读；Photo 和 CV 附件可导出。可读字段中还包含联系方式、出生日期、婚姻等资料。新后台首批招聘列表应只返回业务所需的最小字段，详情、附件、导出分别授权，不自动复制全部可读字段。

## 系统分工

| 环节 | 权限与数据来源 | 执行方式 |
| --- | --- | --- |
| 公开招聘页 | 已审核的公开岗位投影 | 现有服务器同步；不接候选人和员工私有表 |
| 内部身份 | Lark 登录 + 精确公司身份 + 本应用 open_id | 同一个后台入口；链接本身不授予后台权限 |
| 后台准入 | 私有授权名单 | 保持当前单一负责人；角色名称、H25 标签或 Lark 账号不能自动授权 |
| 现有个人业务 | Lark 原生页面 | 员工用本人账号操作，仍由 Base 原有权限控制 |
| 新后台直接读取 | 另行实现并核验的服务端记录、字段、操作规则 | 先核对 Base 上限，之后每个业务接口做受控投影；当前未启用 |
| 发布、建档等写入 | 明确操作者、对象、审批和字段白名单 | 单独业务命令；确认原自动化触发与幂等性后才开放 |
| 定时同步和自动化 | 专用服务身份 | 不代表前台员工；保留现有 AnyCross 执行关系直到逐项迁移 |
| 外部星探 | 独立账户、推荐归属和可撤销登录 | 推荐链接只记录归属；不作为读取候选人、员工资料的通行证 |

## 直接访问的实施路径

1. 整理每个试点人员的实际有效角色、公司身份、经纪人归属、管理范围；不按姓名或不同应用的 open_id 直接拼接。先准备负责人、HR、两名互不共享候选人的经纪人，以及未授权员工的对照场景。
2. 固定首批业务范围：公开岗位、招聘跟进列表和允许的备注。HR 发布/停招、入职建档、异动与考勤写入另行处理，不能随登录一并授权。
3. 如果需要验证用户令牌，在明确权限和数据范围后单独申请最小权限；只保留短期服务端会话，不向前端、URL、日志或 Git 仓库输出令牌。无效或不足的本人权限不使用管理员凭证兜底。
4. 如果当前 Base 的 API 限制使用户令牌方案不可行，新后台需要独立执行权限规则。使用专用服务身份进行数据访问时，权限规则必须先经过审核；服务身份拥有的数据权限不能直接交给员工。未知身份、角色、字段、关联条件或过期权限快照默认拒绝。
5. 服务端绑定公司、人员、业务对象和字段名单。浏览器传入的 Agent、员工 ID、任意 table_id、view_id、字段名不能决定授权范围。需要在服务端核验关联和归属；统计数量、分页、搜索、详情、附件与导出沿用同一规则。
6. 返回给用户的数据按规则投影；禁止先把全表或所有字段发给浏览器再隐藏。不跨用户复用私有结果缓存。关联字段、公式和查找引用也可能泄露其他表内容，逐项确认。
7. 对照 Base 原生页面与新后台结果：同一账号、同一记录和字段；加入跨经纪人访问、字段越权、伪造参数、多角色、撤权、离职、重复提交等验证。不能只用管理员账号验证。
8. 试点通过后逐人开放；同步角色变更和离职撤权后再扩大使用。当前服务器名单撤权已经实现，但不等于自动同步 Lark 离职。

## 当前代码状态

- `access.mjs` 提供准入和操作级校验；非 owner 角色仍只有 Lark 入口。
- `server.mjs` 在岗位数据返回、草稿预览与写入前重新核验当前会话和授权。
- `DraftStore` 在出队及原子替换前重新授权；拒绝后清理临时文件，保留已保存内容。已经提交的操作不会因后来撤权而自动回滚。
- 未添加员工 Base 数据 API，未新增 OAuth scope，未存储员工令牌，也未授权新的真实人员。
- 仍需核验完整角色成员、实际多角色有效权限、其他角色的全量字段、AnyCross 的执行身份与所有写入依赖。
